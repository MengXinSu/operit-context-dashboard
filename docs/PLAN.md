## 二、上游差距清单（9 月中 → 0.87.1）

### dsh-context 新增/重构的能力

| # | 上游功能 | 变更时间 | Operit 侧数据可获得性 | 分档 |
|---|---|---|---|---|
| 1 | **Context Timeline 重构**（原 Trend 卡改名：timelineChart / timelineOverview / timelineDnaBars、`defaultTimelineMode`、新图标） | 11-22 | 已有 steps 数据，纯 UI 改 | ✅ A |
| 2 | **里程碑徽章**（每个 flag 独立计数，todo-add / todo-done / ask 按 items 加权） | 11-22 | steps 数据里有里程碑记录 | ✅ A |
| 3 | **上下文洞察页面**（跨会话：KPI 栏 + 7 天 Token/成本双柱图 + 活动热力图 + 会话卡片，可按时间范围/分组/搜索筛选） | 10–11 月 | raw 按 chatId 分文件，chatmsg 有消息级 token → 可聚合 | ✅ A |
| 4 | **技能加载统计**（哪些技能被加载、次数、最近时间） | — | 需确认 prompt payload 是否含技能注入段 | ⚠️ B |
| 5 | **命令执行统计**（按程序汇总，按派发计） | — | 工具调用日志里有 terminal 命令 → 可解析 | ⚠️ B |
| 6 | **Fleet / Agent 网络**（当前 Agent、父级、子 Agent 实时卡） | 11 月 | Operit2 有 subagents 插件，但 v1 插件拿不到 agent 层级关系 | ❌ C |
| 7 | **`/context` 命令**（弹窗看上下文构成与浏览器） | — | Operit2 v2 有 `registerCoreCommand`，Operit1 无 | ⚠️ B（仅 o2） |
| 8 | **Preferences 卡片**（默认面板入口、时间范围、时间线默认、系统提示词前后缀） | — | 插件自身设置即可 | ✅ A |
| 9 | **Context 面板入口**（右侧边栏标签页） | — | Operit 版是侧边栏 WebView，形态不同 | ⚠️ B |

### 不能直接照搬的原因

dsh-context 的数据源是 DSH 的 session / 模型事件流（host 侧提供 timeline、命令、技能事件）；Operit 版的数据源是 `prompt_finalize` 钩子落盘的 raw payload + chatmsg。**两者数据模型不同，第 4/5 项需要从 raw 里挖或补采集，第 6 项基本做不了。**

## 三、分阶段计划

### P0 · 上游源码基线与 diff（0.5 天）

- [ ] 拉 `bowenliang123/dsh-context` 源码（GitHub，Apache-2.0），锁定 tag `v0.87.1`
- [ ] 与 `operit-context-dashboard/web/src/` 做结构 diff：
  - `App.tsx`（上游多语言 / Operit 版 74 KB）
  - `client/components/*`（donut / stackedBar / trendChart / fileCard）
  - `client/i18n.ts`、`shared/types.ts`
- [ ] 输出「可复用 / 需改写 / 不适用」三栏清单

**验收**：能说清每个上游文件在 Operit 版里对应哪个文件、改动量多大。

### P1 · 数据源映射（1 天）

- [ ] 对第 2 节 A/B 档每项，确认 Operit 侧取数路径：
  - raw payload 里有哪些字段（跑一次真实会话 dump 出来看）
  - chatmsg 的 token 结构
  - 工具调用记录格式
- [ ] B 档两项给结论：能从现有数据挖出来，还是要在 hook 里补采集
- [ ] C 档（Fleet）明确写「不做」，避免悬空

**验收**：一份 A/B 档逐项的「数据字段 → 界面区块」映射表。

### P2 · 采集层扩展（1 天，仅当 P1 判定需要）

- [ ] hook 里补采集需要但当前没落盘的字段（保持「不清洗、不截断」原则）
- [ ] 遵守写盘原则：**每轮一次原子写**（temp → move），不做轮询、不驻留

**验收**：新字段能落盘且文件大小可控（单轮 ≤ 500 KB）。

### P3 · UI 对齐（3.5–4 天，最大块）

> P0 已证明：**上游代码不能搬，只能按设计重实现**（依赖 dsh 私有模型与 UI 包）。详见 [P0-REPORT.md](P0-REPORT.md)。

按优先级：

1. **偏好卡扩项**（0.5 天）—— 4 → 10 项，最便宜、无数据依赖
2. **里程碑采集**（1 天）—— hook 解析 todo/goal/ask → event record
3. **里程碑带 UI**（1 天）—— 抄上游 CSS/图标，聚合逻辑改写
4. **Timeline 主图**（1–1.5 天）—— 改名 + 计数徽章 + 窗口化渲染
5. **上下文洞察页**（+2–3 天，第二波）—— 跨会话聚合，需新增宿主层
6. DNA 条 / 时长曲线 —— **砍掉**（缺组装树模型，硬做只能造假数据）

要求：
- 保持 Operit 版现有设计语言（手机端密度、卡片式布局），不照搬 dsh 的桌面布局
- 图表组件沿用 Operit 版已有的 donut / stackedBar / trendChart，避免双套

**验收**：手机端 WebView 打开后，新旧区块都能正常渲染，无 JS 报错。

### P4 · o2 适配合并 + 打包（1 天）

- [ ] 把 o2.19 的 Operit2 适配层（`Tools.Files` 重定向绕过、`NativeInterface` 坑、UI 加载路径）平移到新代码
- [ ] manifest 保持 `api_version: "2.0.0"`，版本号升 `2.11.0-o2.1`
- [ ] 打包 `.toolpkg`，PC 版先验证

**验收**：PC 版侧边栏打开、数据刷新、切换会话正常。

### P5 · 手机验证与源码归位（1 天）

- [ ] 手机端导入/更新（同 `toolpkg_id` 原地更新）
- [ ] 按功能清单逐项过：Timeline / 徽章 / 洞察页 / 偏好
- [ ] **源码归位**：把 o2.19+ 的 `dist`、`resources`、v1 的 `web/` 源码推到 GitHub（新建 `o2` 分支或同仓库子目录），补构建脚本

**验收**：`git clone` 后能一键重建 `.toolpkg`；手机端功能验收通过。
